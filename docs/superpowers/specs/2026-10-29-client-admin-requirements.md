## 1. 产品目标与用户

第一版面向普通个人客户，一个账号对应一个独立用户。

客户安装 Windows 客户端，自行注册或使用管理员创建的账号登录。客户不需要配置模型服务商、接口地址或 API Key，即可使用管理员提供的模型和应用。

运营者通过独立部署在自己服务器上的后台管理用户、模型、应用权限、售价、兑换码、赠送余额和客户端版本。

第一版不做家庭、班级、企业组织和员工分权体系。

## 2. 系统边界

| 部分 | 运行位置 | 职责 |
| --- | --- | --- |
| Windows 客户端 | 客户电脑 | 应用界面、本地数据、项目文件、终端、电脑操作、学习模块 |
| 管理后台 | 运营者服务器 | 运营者维护账号、应用、服务配置、计费、兑换码和版本 |
| 统一接口服务 | 运营者服务器 | 注册登录、鉴权、授权、模型转发、并发控制、余额预留与结算 |
| 外部服务 | 配置的服务商 | 提供模型及其他收费 API 能力 |

模型调用链路：

```text
客户客户端
  -> 运营者接口：账号校验、应用与模型授权、并发与余额检查
  -> 使用服务端保存的凭据调用服务商
  -> 返回结果与可核实用量
  -> 结算余额、记录账单
```

模型和共用服务的 API Key 不打包进客户端，也不在登录后下发到客户端。客户持有的是自己的登录凭证，不是运营者的服务商密钥。

文件、终端和电脑操作在客户电脑上执行，不能因客户端接入云端账号而转移到运营者服务器执行。

## 4. 用户账号

### 4.1 注册与登录

- 支持客户自行注册，也支持管理员创建客户账号。
- 自助注册采用邮箱验证码和密码。
- 登录采用邮箱与密码。
- 支持通过邮箱验证码重置密码、登录后修改密码、退出登录。
- 管理员可停用账号、处理密码重置，并撤销账号登录状态。
- 普通用户注册不能获得管理员身份或访问后台接口。

### 4.2 默认应用权限

- 新注册用户默认开放全部现有应用功能。
- 管理员可调整之后新用户的默认权限。
- 管理员可单独启用或关闭某个用户的应用权限。
- 应用可见与付费调用能力分开判断：有功能权限但余额不足时，不能继续发起收费调用。
- 不产生在线模型或收费服务费用的本地功能、课程不因零余额自动收费或被统一关闭。

### 4.3 设备与会话

- 默认每账号最多 3 台设备登录，管理员可调整设备上限。
- 用户可以查看自己的登录设备并退出指定设备。
- 管理员可以强制指定设备下线。
- 达到设备上限时，需要释放已有设备名额，不静默挤掉正在使用的设备。
- 设备上限与模型调用并发上限独立管理。

最后一项设备满额处理属于本文的实施建议，尚未单独询问；实现前应随整体方案评审确认。

## 5. 管理员与后台

第一版采用一个独立的超级管理员账号，不做客服、财务、运营等多角色分工。

后台需要覆盖：

| 页面 | 核心操作 |
| --- | --- |
| 用户管理 | 查询账号、创建账号、启用/停用、重置密码、撤销会话 |
| 用户详情 | 应用权限、设备列表、余额分类、账单、赠送及兑换记录 |
| 应用管理 | 默认权限、应用默认模型、允许使用的模型范围 |
| 模型与服务 | 服务商配置、密钥维护、模型能力、连接测试、启用停用 |
| 价格管理 | 输入/输出 Token 售价及其他可计量单位售价 |
| 兑换码 | 批量生成、查询、导出、作废、查看兑换归属 |
| 注册赠送 | 开关、金额、有效期规则 |
| 账务管理 | 消费明细、异常待核查、人工余额调整、退款关联记录 |
| 客户端版本 | 发布版本、更新说明、安装包信息 |

用户设备上不部署运营者管理后台。管理员权限必须由服务端验证，不能仅靠隐藏页面或按钮实现。

## 6. 模型与外部服务

### 6.1 复用现有能力

以项目已有的服务商目录、协议适配和模型配置能力为基础，不另行指定一套全新的供应商体系。

现有源码中包含 DeepSeek、阿里云百炼、Kimi、MiniMax、火山方舟、智谱、OpenAI、Anthropic、Gemini、OpenRouter 和 Ollama 等目录或适配入口。

以上仅代表项目当前代码能力，不承诺每个供应商、模型或接口都能从部署服务器正常调用。正式开放前需验证连通性、能力和用量返回。

管理员可以：

- 管理服务商、接口地址、密钥和模型。
- 为各应用指定默认模型与可选模型。
- 启用、停用模型，配置售价。
- 测试连接，检查模型与应用需要的能力是否匹配。

客户可以：

- 查看被授权的模型及其价格。
- 在应用允许的模型范围内切换。
- 使用应用预设的默认模型。

客户不可以自行添加服务商地址、模型接口或 API Key。不能只在界面移除入口，服务端也须阻止未授权模型调用。

需要图片输入等特定能力的应用，只展示符合其能力要求的模型。

### 6.2 共用服务与个人账号

- 联网搜索等产品共用 API 服务由管理员统一配置。
- 共用服务密钥保留在服务端，不下发客户端。
- 收费服务按后台配置规则计费。
- 客户自己的 GitHub、邮箱等个人账号，由客户单独授权；不得共用运营者个人账号。
- 纯本地算法、浏览器内训练等不发起收费服务请求的功能，不计入在线模型消费。

## 7. 计费与余额

### 7.1 收费模式

采用预充值余额、按实际用量扣费，不采用月费套餐。

- 以人民币余额向用户展示可用资金和账单。
- 文本模型分别配置输入 Token 与输出 Token 售价。
- 单价展示建议统一使用“元/百万 Token”，计算使用实际数量。
- 一次任务发生多次模型调用时分别记录，并可按任务汇总。
- 非 Token 计费服务按其实际可核实单位计费，例如图片张数或音频时长，不能强行折算成 Token。
- 使用前向用户展示对应服务的收费标准。
- 售价由管理员设置，与服务商成本价格分开。
- 更改售价后，新发起调用使用新价；历史账单和已开始的调用保留其价格快照。

缓存 Token、推理 Token、图像/音频 Token 等供应商用量字段的映射，属于待完成的技术适配细则。不得重复计量已经包含在输入或输出总量中的字段，也不得把估算值伪装成准确用量。

### 7.2 不允许透支

- 调用前检查权限和余额，并预留资金。
- 完成后按实际费用结算，释放未消耗的预留金额。
- 多设备、多请求共享同一余额，不能并发超扣。
- 余额不足时停止发起新的收费调用，提示用户兑换充值。
- 自动化任务已完成的结果保留，已经产生的有效用量正常结算。
- 充值后可以继续使用；具体任务是否支持恢复执行沿用原有工作流，不默认重放已经发生副作用的操作。

预留额度如何计算、超时释放及迟到用量如何处理，应在开发设计中明确，但不引入透支或按估算强行扣费。

### 7.3 异常与取消

- 未提交给服务商的请求不扣费。
- 用户取消或中途断线，若服务商返回准确用量，则按实际消耗结算。
- 无法取得准确用量的异常请求记录为待核查，不凭估算直接扣费。
- 账单区分完成、取消、异常待核查等状态。
- 同一次调用的回调、重试通知或结算重入不得重复扣费。

## 8. 兑换码充值

第一版不接在线支付。

- 管理员可批量生成兑换码。
- 可设置面值、生成数量、兑换截止日期。
- 每个码只能成功兑换一次。
- 面值由服务端确定，客户端不能自行提交修改。
- 重复提交、并发兑换不能重复入账。
- 兑换成功后增加用户充值余额。
- 兑换到账的充值余额长期有效。
- 后台可查询未兑换、已兑换、已过期、已作废状态。
- 可查询兑换账号、兑换时间及关联入账记录。
- 未兑换的码可作废；支持导出以便管理员自行发放。

兑换码销售或发放的外部流程不在第一版支付系统内。

## 9. 注册赠送

- 后台控制注册赠送是否开启、赠送金额。
- 每个账号只领取一次注册赠送。
- 配置调整只影响之后注册的用户，不重复给已有账号发放。
- 赠送金额与兑换充值金额分别记录来源。
- 赠送余额可设置长期有效，或领取后若干天有效。
- 优先消耗即将到期的赠送余额，再使用长期有效余额。
- 兑换充值余额始终长期有效。

赠送资金与长期资金在并发预留、结算、取消时应保持来源和有效期归属，不能因退款或释放预留改变成另一种资金。

## 10. 余额调整与退款

- 第一版不做自动退款。
- 客户退款和扣费纠错由管理员人工处理。
- 后台支持补回误扣、增加或减少余额。
- 每笔调整要求填写原因，记录操作人、时间、调整前后金额。
- 涉及实际资金退款时，管理员在外部完成，再关联后台记录。
- 已有消费账单不直接删除或改写，通过关联调整记录纠正。
- 赠送余额、充值余额和真实外部支付不能混为同一种款项。

人工调整的账务实现也需遵守不重复入账、禁止无记录修改余额等原则。

## 11. 并发控制

采用用户确认后的简化方案：

- 默认同一账号最多同时处理 3 条模型请求，后台可调整。
- 聊天、定时任务和自动化任务共用该账号的模型请求并发额度。
- 第一版不做等待队列。
- 超出时明确提示当前请求较多，请稍后重试。
- 已有请求继续处理，不挤掉登录或中断其他设备。
- 未提交给模型服务商的被拒绝请求不扣费。

并发限制按实际模型请求计算，不直接等同于任务数量；一个任务可以产生多次调用。

## 12. 数据存储与隔离

### 12.1 本机

- 聊天记录、学习进度及其他个人应用数据按账号保存在客户电脑。
- 第一版不做跨设备同步。
- 同一台电脑退出账号或切换账号时，不显示另一账号的数据。
- 学习 iframe 的 localStorage、IndexedDB、缓存等也纳入账号隔离，不能只隔离主聊天数据库。
- 切换账号不能把旧账号仍运行的任务、会话或结果归到新账号下。
- 文件、终端及系统权限仍受原项目机制和客户操作系统权限控制。

### 12.2 服务端

服务器统一保存账号、权限、设备会话、模型与共用服务配置、价格、兑换码、余额、用量账单和运营审计记录。

模型请求所需内容会经过运营者接口发送至服务商，但管理后台默认不额外保存聊天正文。错误日志、请求日志和管理页面也不应意外记录或展示正文、密钥及凭证。

注册验证码、密码、登录凭证和服务商密钥需采用适合各自用途的安全处理方式；密码不能以明文或可逆加密方式存储。

## 13. 离线使用

- 首次登录需要联网。
- 已有账号断网后可查看本地历史记录、文件和已下载课程。
- 模型调用和其他依赖外部服务的操作提示联网后重试。
- 余额、应用权限和账号状态以服务器为准，不能依据客户端旧缓存继续产生收费调用。
- 重新联网后校验最新账号状态、权限和余额。

离线模式不代表服务器能即时收回已经下载到客户电脑上的资料，也不应承诺做到这一点。

## 14. 客户端交付与更新

- 第一版支持 Windows 10/11 64 位。
- 暂不交付 macOS 版本。
- 运营者在后台发布客户端版本与更新说明。
- 客户端检测更新并提示，由客户确认安装。
- 有任务运行时不自动重启。
- 第一版不做强制更新。
- 服务器模型、权限和价格变更通过服务端生效，不要求客户每次重新安装客户端。

安装包签名、更新包完整性验证、版本兼容、下载地址与发布操作校验属于后续技术设计事项，不能仅靠客户端显示一个下载按钮视为完整更新能力。

- 强制更新。

## 18. 实施建议

以下为开发人员建议，不冒充访谈中已确认的技术实现：

1. 在同一仓库增加独立云端服务与后台，客户端保留本地运行能力；不直接把现有单用户 Web 服务作为多客户共享运行环境公开。
2. 先完成服务端账号、应用授权和密钥边界，再改造客户端模型调用。
3. 钱包采用有精度约束的金额表示和可追踪流水。避免浮点累计误差，微小费用不能因每次四舍五入而无故归零或放大。
4. 兑换、赠送、预留、扣费和人工调整使用事务及幂等标识，保证多设备并发下只处理一次。
5. 服务端根据实际会话身份选择用户、应用和模型配置，不接受客户端伪造的用户编号、售价、余额或 Token 数量。
6. 注册验证码、登录、兑换码尝试等入口需防重复提交和基础滥用限制；不能因有邮箱验证就宣称杜绝批量领取赠送。
7. 原有本机服务和学习 iframe 在分发客户端中需统一纳入账号上下文，现有独立端口的无账号 API 不能作为绕过计费的新入口。
8. 模型不可用时先报告实际错误，不默认切换到不同价位的收费模型。是否增加自动降级由后续单独决定。
9. 以服务商返回的实际用量为结算依据；管理员连接测试等运营调用单独记录，不记到某个客户余额。
10. 有限设备登录、网络中断和强制下线不能被设计成云端删除客户本机文件或改变其电脑权限。

## 19. 验收清单

### 19.1 账号与权限

- 邮箱验证码注册成功，密码登录、找回密码、修改密码和退出登录可用。
- 后台创建账号与用户自行注册均生成普通客户，不产生后台权限。
- 普通客户不能访问管理接口、读取供应商密钥或修改售价。
- 账号停用、会话撤销后，新的在线模型请求被拒绝。
- 新用户默认拥有全部功能；后台单独关闭某应用后，服务端阻止该应用的收费调用。
- 默认 3 台登录设备，设备查看、退出和管理员强制下线可验证。

### 19.2 资金与并发

- 同一兑换码并发提交只成功入账一次；过期、作废、已兑换代码不能再次充值。
- 注册赠送按当时配置发放一次，规则调整不会重复赠送已有账号。
- 赠送到期、消费顺序和长期充值余额正确区分。
- 输入/输出 Token 与其他计量服务按对应价目结算，用户可查看价格和明细。
- 模型涨价不更改历史账单或已开始调用的价格快照。
- 多设备并发不能产生重复扣费或透支。
- 超出并发上限时不排队、不提交服务商、不扣费，已有任务继续运行。
- 未提交调用、已返回准确用量的取消调用、缺失用量的异常调用分别按规则处理。
- 人工调整必须有原因和关联流水，历史账单不被覆盖。
- 金额计算和微小用量计费有边界测试。

### 19.3 客户端与完整功能

- 客户无需填写供应商 API Key，即可使用后台授权模型。
- 主聊天、学习模块及现有其他收费调用统一经过服务器鉴权和计费。
- 关键功能回归覆盖 Skills、插件/MCP、定时任务、文件、终端及电脑操作。
- 客户本机操作不会转为运营者服务器上的操作。
- 切换账号后，主应用及 iframe 内个人数据均不串号。
- 断网可查看已有本地资料，在线收费功能不会绕过余额验证。
- 重新联网后权限、账号状态和余额更新。
- 发布版本后客户端提示更新，用户确认才安装，有任务时不自动重启。

### 19.4 部署与运营

- 在计划服务器规格上验证资源占用、并发拒绝和媒体转发边界。
- 后台、接口、客户端均不在日志或响应中暴露服务商密钥。
- 验证数据库备份恢复，资金流水与账户余额恢复后一致。
- 实际可用模型、注册邮件和更新分发通过真实环境验证。
- 明确区分测试通过、真实服务验证和商业发布授权；未完成项不能以“已上线可商用”描述。

## 20. 建议开发顺序

1. 账号、管理员权限、用户管理及后台基础页面。
2. 服务商与模型管理、应用授权、客户端统一调用。
3. 钱包、兑换码、注册赠送、计量与结算、人工调整。
4. 客户端账号数据隔离、设备管理、离线与完整功能回归。
5. 版本发布与更新、部署、备份恢复、压测和试用验收。

以上是实施分阶段顺序，不是将最终交付范围缩减为只完成前几项；也不表示已开始执行。
